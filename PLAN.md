# MacNexus — Development Plan

**Версія:** 0.1.0  
**Статус:** Active Development  
**Платформа:** macOS, Apple Silicon  
**Мова:** Python 3.12  
**GUI:** PySide6  
**Тестування:** unittest  
**Статичний аналіз:** Ruff

---

## 1. Призначення

MacNexus — локальний застосунок для моніторингу Mac, аналізу дискового простору та безпечного обслуговування системи.

Основні принципи:

- Local-first та Privacy-first.
- Безпечна робота з файловою системою.
- Жодного автоматичного видалення.
- Модульна архітектура.
- Автоматизоване тестування.
- Контроль використання системних ресурсів.
- Передбачувана поведінка під час роботи з великими обсягами даних.

## 4. Архітектура

Основні частини:

- `app` — запуск і налаштування застосунку.
- `ui` — вікна, сторінки, віджети та моделі UI.
- `services` — бізнес-логіка та робота з системою.
- `models` — структури даних.
- `tests` — автоматизовані тести.

Правила архітектури:

- Не розміщувати бізнес-логіку у віджетах.
- Не перевантажувати MainWindow.
- Відокремлювати UI від сервісів.
- Використовувати фонові потоки для тривалих операцій.
- Тестувати сервіси незалежно від UI.
- Не створювати порожні модулі наперед.
- Не додавати залежності без практичної потреби.
- Мінімізувати зв'язність між модулями.

## 5. Безпека

- Не змінювати оригінали під час сканування.
- Не видаляти файли автоматично.
- Не сканувати системні директорії без необхідності.
- Коректно обробляти відмови в доступі.
- Не переходити за symlinks без визначеної політики.
- Перед видаленням показувати шлях і розмір.
- Використовувати системний Trash.
- Передбачити захист критичних системних файлів.
- Не виконувати потенційно руйнівні операції без явного підтвердження користувача.

## 8. Поточний стан

**Поточний етап:** Етап 4 — Disk Analyzer.  
**Поточне завдання:** оцінка продуктивності та оптимізація роботи з великими наборами даних.

Реалізовано:

- Dashboard та системні сервіси.
- File Scanner із фоновим пакетним скануванням.
- Disk Analyzer на базі QTableView і власної моделі.
- Фонове сортування за розміром.
- Обробка помилок і скасування сканування.
- System Junk із трьома категоріями.
- Фонове сканування System Junk.
- Відображення результатів у таблиці.
- Інтеграція System Junk у навігацію.

**Автоматичні перевірки на останній контрольній точці:**

- unittest — 94 тести пройшли.
- Ruff — успішно.
- compileall — успішно.

**Benchmark на 337 000 записів:**

| Операція | Час |
|---|---:|
| Створення записів | 0,73–0,74 с |
| Додавання до моделі | 0,63–0,64 с |
| Сортування за назвою | 10,41 с |
| Сортування за розміром | 9,90 с |
| Сортування за датою | 11,73 с |
| Сортування за шляхом | 21,70 с |
| Пікова RAM | близько 342 MB |

Ці показники є результатами попереднього benchmark моделі та proxy, а не повного вимірювання чутливості GUI. Їх потрібно повторно перевірити на актуальній реалізації Disk Analyzer.

Залишилося:

- Порівняти кешування шляхів із варіантом без кешу.
- Перевірити вплив оптимізацій на RAM.
- Провести окреме тестування реального інтерфейсу на великих наборах даних.
- Перевірити поведінку UI під час тривалого сканування та сортування.

## 9. Правила розробки

1. Працювати послідовно, невеликими завершеними кроками.
2. Перед змінами перевіряти поточний стан файлів.
3. Не переписувати робочі модулі без необхідності.
4. Спочатку реалізовувати бізнес-логіку, потім інтегрувати її в UI.
5. Пояснювати призначення нових модулів і змін коду.
6. Після змін запускати відповідні тести, Ruff та compileall.
7. Не додавати функції поза поточним етапом без узгодження.
8. Перевіряти продуктивність вимірюваннями, а не припущеннями.
9. Не переходити до наступного етапу, поки поточна функціональність не перевірена.
10. Підтримувати модульність, читабельність і тестованість коду.
11. Не створювати зайву абстракцію без практичної потреби.
12. Зберігати стабільність уже реалізованих модулів під час розширення застосунку.
